# ADR-0013: Fixed local SSH port, local-only client, and app-visible autostart

## Status

Accepted and implemented in `infrastructure/` for the fixed-port and autostart
slices. The presentation wiring of `RuntimeHostService.ensureRunning` and the
removal of the remote-SSH surface landed in the launcher slice (ADR-0014).

## Context

The shipped runtime used three loosely coupled conventions that no longer match
the product:

1. **Guest SSH used an ephemeral candidate port.** `GuestSshdWorkload` proposed
   a random port from the IANA dynamic range, waited for the daemon's own
   `Server listening on 127.0.0.1 port N.` report, and retried with the next
   candidate on a bind failure (`LoopbackPortCandidates`, up to four attempts).
   That is the right shape for a multi-tenant host that must avoid collisions,
   but this app owns exactly one guest and needs a stable endpoint: the
   host-key pin, the readiness frame, the notification text, and the terminal
   attachment all describe the same thing, and a retry loop hides a real
   conflict behind a moving port.
2. **The SSH client could dial anything.** `SshClientBridge`/`SshSessionConfig`
   are a generic remote-host client, and the terminal's "Remote SSH host"
   dialog passed a user-entered host and port straight through. The product
   direction is that the app is not an SSH client for external hosts: the
   terminal is a local view of the Linux this app runs.
3. **Starting Linux was a user lifecycle action.** The launcher owned a
   `Start session` / `Stop session` control, and nothing started the runtime
   automatically. The product wants Linux to behave like a system component:
   open the app and it is there, background the app and it keeps running.

Android's own constraint does not change: ongoing work must be user-visible and
stoppable through a foreground-service notification, and a runtime must not be
started from a background trigger the user never initiated.

## Decision

1. **One documented fixed loopback port: `127.0.0.1:22022`.**
   `LocalSshEndpoint` is the single source of the host, port, and host-key
   scope, used by the launching side (the guest daemon's `-p` argument and the
   pin) and the dialing side (the client config). The port sits below the Linux
   ephemeral range (typically 32768–60999) so an outgoing connection can never
   occupy it, and it is unassigned by IANA.

2. **No candidate selection and no retry for guest SSH.**
   `LoopbackPortCandidates` and its test are deleted. `GuestSshdWorkload` makes
   exactly one attempt on the fixed port. The daemon's own bind report still
   attributes the endpoint: a `BIND_FAILED` line becomes the typed
   `GuestSshdBindFailureException`, the start ends in `FAILED` with that reason,
   and the tracer is torn down. The host never probes-and-attaches: a listener
   it did not start is never published as the endpoint.

3. **The production SSH API cannot name a host or a port.**
   `LocalSshSessionFactory` is the only production configuration path. It takes
   the initial PTY size and nothing else, and builds the config from
   `LocalSshEndpoint`, the app-managed Keystore credential
   (`KeystoreBridgeCredential.CREDENTIAL_ID`), and the fixed host-key scope.
   `SshSessionConfig` and `SshClientBridge` stay for internal and test use.
   `LocalSshSessionFactory.pinnedHostKeyOnly()` refuses a host key this app did
   not pin, so even a listener that somehow held the fixed port could not be
   attached to.

4. **The host-key pin is mandatory, not best-effort.**
   The guest host key is generated by the app into its private overlay and
   pinned before readiness is published. A pin that cannot be stored now fails
   the start (`FAILED`) instead of degrading to a first-contact prompt: the
   local-only client has no first-contact path, so an unpinnable endpoint is not
   attachable and must not be reported ready.

5. **`ensureRunning` is the autostart boundary.**
   `RuntimeHostController.ensureRunning` starts a session only when no session
   is live; `STARTING`, `RUNNING`, `RECONNECTING`, `STOPPING`, and `RECOVERING`
   are left alone and re-published. `RuntimeHostService.ensureRunning(Context)`
   is the thin Android adapter an Activity calls from a foreground event. The
   runtime identity (`appId`, `version`) comes from the curated catalog and the
   session id is generated by the host, so the caller supplies nothing.

6. **No forbidden background start.**
   There is no boot receiver, no `RECEIVE_BOOT_COMPLETED` permission, no job,
   alarm, or sticky-restart path, and the host service stays unexported. Linux
   starts only from a user-visible launch. `RuntimeAutostartManifestTest` guards
   this at the manifest level.

7. **The notification stays, and stays stoppable.**
   The ongoing notification and its `Stop` action remain because Android
   requires foreground work to be user-visible and user-stoppable. It gains a
   content intent (resolved through `PackageManager`, never by naming a
   presentation class) so tapping it returns to the app, which is where the
   runtime autostarts. The `STOPPED` copy now says "Open the app to start it
   again" because that is the only start path.

Rejected alternatives:

- **Keep the ephemeral candidate plus a documented fixed-port fallback.** The
  fallback would be the normal path (the port is fixed), so the app would carry
  two endpoint contracts and two failure modes for one guest. It also keeps the
  retry loop that hides a real conflict.
- **Pre-bind the fixed port host-side to prove it is free.** A reserve/release
  window is exactly the race the port contract forbids: the daemon must bind and
  report, or the start must fail.
- **Attach to whatever answers on the fixed port when our daemon fails to
  bind.** That is a foreign-listener attachment; the endpoint would be reported
  `RUNNING` without the app owning it.
- **Remove the notification because the UI no longer shows a session.** Android
  requires ongoing foreground work to be visible and stoppable; hiding it would
  trade a platform rule for UI cleanliness.
- **Start Linux from `BOOT_COMPLETED` or a job so it is "always on".** That is
  a background start the user never initiated, it needs a boot permission, and
  it would not survive OEM battery policy anyway.
- **Keep the remote SSH dialog as a power-user feature.** The app is not an SSH
  client; a user-chosen external host needs its own credential/trust policy and
  its own decision record.

## Consequences

- The endpoint is stable across restarts, so `127.0.0.1:22022` is what the
  notification, the readiness frame, and the terminal config all name. A second
  app or a leftover process holding 22022 produces a typed `FAILED` naming the
  conflict, not a silent move to another port.
- `GuestSshdBindFailureException` is the first typed workload failure: the
  reason text is deterministic and unit-tested, and the workload no longer
  retries.
- The local-only client closes the first-contact trust path for the local
  endpoint. The generic `SshClientBridge` keeps its behavior for tests; the
  production caller in `presentation/terminal` (`TerminalAppView`) builds its
  `SshSessionConfig` through `LocalSshSessionFactory` and applies
  `LocalSshSessionFactory.pinnedHostKeyOnly()`, so no production path can name a
  host or a port. The remote-host surface has been removed.
- Autostart is idempotent, so repeated Activity foreground events cannot start a
  second daemon. The observable limitation is that tapping the notification's
  `Stop` while the app is in the foreground leaves the runtime stopped until the
  next foreground event (leaving and reopening the app); there is deliberately no
  in-app start control.
- Everything above is verified by unit tests and the manifest guard. Device
  behavior for the fixed port and background continuation is recorded in
  `docs/test-plan.md`; API-level limits (background-start and FGS-type
  restrictions on newer Android) remain as documented in
  `docs/limitations.md`.
