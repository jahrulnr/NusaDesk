# ADR-0050: Bluetooth capability surface (NusaDesk-native)

- Status: accepted
- Date: 2026-09-23

## Context

The 2026-09-23 permission recheck found `BLUETOOTH_CONNECT`/`BLUETOOTH_SCAN`
(plus the capped legacy pair) declared in the manifest with no capability
behind them: no `BluetoothAdapter` reference anywhere in the source, no bridge
module, no guest command. The same pass established that upstream Termux:API
has **no** bluetooth client command (and the GPL app's receiver has no
bluetooth action), so there is no parity contract to follow — this is a
NusaDesk-native surface, not parity work.

The platform matrix (`docs/research/platform-capability-matrix.md`) splits the
domain into what a third-party app can legally do and what it cannot:

- possible with the declared grants: adapter state/name, bonded devices,
  classic discovery, `createBond`, `ACTION_REQUEST_ENABLE`,
  `ACTION_REQUEST_DISCOVERABLE`, BLE scan, GATT client and server, RFCOMM
  client and server, BLE advertise;
- hard limits: adapter MAC address (`LOCAL_MAC_ADDRESS` is
  signature|privileged), programmatic enable/disable for a target-33+ app,
  unpair (`removeBond` is `@hide`), OBEX file transfer, PAN tethering, HID
  *host*, and bonded-device battery level (all `@SystemApi`/absent from the
  public SDK).

`BLUETOOTH_ADVERTISE` was the one missing declaration (BLE advertise and
classic discoverability on API 31+); it is now declared with its rationale and
pinned by `BridgePermissionsManifestTest`.

## Decision

1. **Four bridge modules under one `bt.*` namespace.** `BluetoothModule`
   (adapter state, bonded devices, discovery, pair, consent requests),
   `BluetoothLeModule` (BLE scan, advertise), `BluetoothGattModule` (GATT
   client and a fixed GATT server), `BluetoothRfcommModule` (RFCOMM serial).
   They register through `CapabilityModules`, so the domains stay independent
   and parallel work never touches the bridge or the handler.
2. **Consent, never silent control.** `bt.enable.request` and
   `bt.discoverable.request` run through the capability foreground host
   (`BluetoothConsentForegroundOperation`) and answer with the platform's own
   result; the app never turns the radio on by itself.
3. **Hard limits are typed absences, not fake features.** `bt.unpair` always
   answers `bt-unpair-unsupported:platform hides removeBond; use the system
   Bluetooth settings`; the adapter MAC address is never reported; OBEX, PAN,
   HID host, and battery level are documented as unavailable in the guest doc.
4. **Bounded by construction.** Discovery runs a 12 s window; `bt.pair` waits
   at most 30 s for the bond broadcast; GATT connect is bounded at 30 s and
   I/O at 10 s; RFCOMM read/write carry explicit timeouts and an 8 KiB read
   cap; row/buffer caps apply to every list (50 rows, 128-notification
   buffer). One discovery, one LE scan, one GATT client session, one GATT
   server, and one RFCOMM session at a time; `close()` releases all of them.
5. **Guest CLI is native.** `nusadesk-bt` is generated by `GuestBtCliWriter`
   into `/usr/local/bin` and rewritten on session start like every managed
   guest file. Verbs map 1:1 to bridge methods, print the bridge JSON, and
   keep the contract exit codes (0 result, 1 typed error, 2 usage, 5 bridge
   unreachable). `--seconds`-style waits are bounded and the script never
   sees the session token.
6. **RFCOMM ships as a bounded proxy first.** A socket fd hand-off to the
   guest (the ADR-0041 `SCM_RIGHTS` channel) stays a documented follow-up:
   the proxy proves the use case without widening the fd surface in the same
   change.
7. **Permissions are checked per call** through `AndroidPermissionChecker`
   (API 31+ SCAN/CONNECT/ADVERTISE, legacy install-granted pair below), and a
   missing grant is a typed `bt-permission-required`/`-denied`, never a
   prompt from the bridge.

## Consequences

- A guest script can now inventory and drive the phone's Bluetooth: read
  adapter state, list bonded devices, discover, request pairing, scan BLE,
  talk GATT (client and server), and run a serial link over RFCOMM — all
  through bounded bridge methods with honest typed errors.
- The bluetooth declaration set is no longer inert: `BLUETOOTH_CONNECT`,
  `BLUETOOTH_SCAN`, `BLUETOOTH_ADVERTISE`, and the capped legacy pair each
  back a shipped method.
- The remaining hard limits are documented in the guest doc and reported as
  typed absences, so a script cannot mistake "not possible" for "broken".
- Unit coverage: `BluetoothModuleTest` (31), `BluetoothLeModuleTest` (25),
  `BluetoothGattModuleTest` (30), `BluetoothRfcommModuleTest` (26),
  `GuestBtCliWriterTest` (3). Device verification on the S10e (and the S7
  Edge as the peer) is the acceptance gate and is recorded in
  `docs/evidence/` when it lands.

## Device evidence

Verified on the S10e (SM-G970F, Android 12/API 31) on 2026-09-23/24 through
the live guest: `nusadesk-bt status|devices|discover|le-scan|advertise`,
`bt.unpair` (typed absence), `bt.gatt.server.start|stop`, and
`bt.rfcomm.listen` (bounded timeout). Advertising answered the typed
permission error before the grant and started after it. On 2026-09-24 the
peer-dependent rows were closed with the S7 Edge (SM-G935F, Android 10/API 29)
as the peer: the S7's LE scan saw the S10e's advertisement carrying our service
UUID, the S7's GATT client connected to the S10e's GATT server, discovered the
`7a1f0001-…` service, wrote to it, subscribed, and received the S10e's
notification ("dari-S10e"), and an RFCOMM echo ran both ways
("ping-dari-S7" / "pong-dari-S10e") after the pair consent dialogs were
confirmed. Two device findings were fixed afterwards: the `bt.pair` timeout
report (the module now re-reads `getBondState()` before answering) and the BLE
advertise payload (the device name is omitted from the advertisement when a
128-bit service UUID is present, and platform error codes map to specific
typed errors). Full observed output in
`docs/evidence/capability-closure-matrix.md`.
