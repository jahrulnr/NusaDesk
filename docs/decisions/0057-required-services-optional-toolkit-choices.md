# ADR-0057: Required guest services, independently optional USB/ADB and Termux commands

## Status

Accepted. Supersedes ADR-0055's single optional "Guest services & tools" bundle and amends ADR-0017, ADR-0037, and ADR-0043. The previous decision and its device evidence remain as history, not the current installation contract.

## Context

The first-install checkbox from ADR-0055 bundles `systemctl`, Python, USB/ADB and Termux commands. This is the wrong boundary: the service manager/Python overlay is part of the usable PRoot session, while USB access and Termux command compatibility are independent user needs. A person may choose neither, either, or both. The earlier System page offered one action and displayed the other two as mere dependent status pills.

The service overlay contains the pinned Python interpreter, `systemctl`/`service`, and compose tooling. Guest `android-cli` and other NusaDesk-native bridge clients share a module named `termux_compat.py`; its name does not make those native clients opt-in Termux commands. It must remain present when the `termux-*` command surface is absent. USB/ADB scripts and `termux-*` scripts are generated by guest writers rather than supplied as independent downloaded archives. Optional installation therefore provisions only the chosen set, with state tracked in the guest rootfs.

## Decision

1. The required setup pipeline is Ubuntu Base rootfs → guest OpenSSH → the verified service/Python bridge overlay. Launcher readiness, in-app autostart and boot opt-in all require all three. Failure of the bridge is a setup failure with an explicit retry, not an SSH-only success. Already-installed overlays are reused; no download is repeated for them.
2. The first-install choice offers two separate, unchecked options: **USB / ADB driver** and **Termux commands**. None, either or both may be selected. The selected writer(s) run only after the required overlay succeeds, serialized by the same install lock. A user may install either later from its own action under System → One-click install. No arbitrary package or URL input is introduced.
3. Toolkit state is independently persisted under the guest rootfs, not inferred from the shared Python overlay. A fresh rootfs starts with neither optional toolkit; session-start reconciliation updates only previously installed toolkit files. On an upgrade from the previous all-bundled writer, existing toolkit files are adopted so existing users keep working; a missing option is never silently enabled just because the service overlay exists. A session that predates a later install may need a restart for its bindings/processes to see the new toolkit.
4. Core generated files remain usable independently of these options: shared bridge module and `android-cli`/NusaDesk-native capability clients stay installed with the required session. Termux's named client scripts/docs and USB/ADB clients/driver launchers are installed only for their respective option. A generated-file sweep must not delete unrelated user files or the shared bridge runtime.
5. The passive first-install reassurance footer ("Private by default", "Verified before run", "Ready for the background"), the static "Set up your Linux desktop" heading, and the storage/ABI/network requirements card are removed. The optional toolkits render as plain checkbox rows directly on the setup surface — no nested card — so the screen spends its space on progress and the two actual choices while the primary action stays visible.

## Consequences and verification

- The setup surface sits directly on the launcher backdrop (no card) and its
  single action is a bottom-pinned footer, so the page never looks like an
  empty card with a floating button; the terminal carries a faint dim-green
  math-art backdrop under its white text.
- The System page reports each toolkit's own disk-backed Not installed / Installing / Installed / Failed state and one actual Install or Retry action. The required service bridge is described as included with Linux setup, not offered as an optional purchase or toggled off.
- Test fresh-rootfs provisioning for all four choices, upgrade adoption, idempotent session restart, independent System installs, and required bridge failures. Verify the UI and guest command availability on an ARM64 device; an APK build alone cannot prove the PRoot/USB path. Device run 2026-09-27 on the S10e (Android 12/API 31) covered TOL-001–005 in `docs/test-plan.md`: core-only, per-toolkit System installs, and both-ticked first install.
- ADR-0055's OPT-001–005 device checks document the older bundled behavior, not evidence for this revised choice model.
