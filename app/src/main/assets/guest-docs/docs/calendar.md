# Calendar (read and bounded write)

NusaDesk exposes the user's own Android calendars to the guest: a
bounded read of upcoming events and bounded create, update, and
delete calls. It never touches attendees, never writes an attendee
row, and never sends an invitation, so a guest automation cannot mail
other people on the user's behalf.

## Permissions

- `calendar.list` needs `READ_CALENDAR`
- `calendar.insert` / `calendar.update` / `calendar.delete` need
  `WRITE_CALENDAR`

The app never opens a consent dialog from the guest. A missing grant
is a typed error the script can report: `calendar-permission-required`
when no decision was recorded, `calendar-permission-denied` when the
user previously refused or revoked it. The grant is the user's own
decision from Android App Info.

## Reading upcoming events

`nusadesk-android calendar list` reads the provider's instance table
for a fixed window: from now to seven days later. The window and the
row limit are owned by the host; the guest cannot widen them.

Each event row carries:

- `event_id`, `title`
- `begin_utc_ms`, `end_utc_ms` - UTC milliseconds
- `all_day` - an all-day event spans whole UTC days
- `calendar_id`, `calendar_name`, `timezone`
- `location` - only when the event has one

The response also carries `count` and `truncated`. At most 50 rows are
returned; `truncated` = `true` means more events fell inside the window
than the read could return, so a bounded answer never looks complete.
Because the read goes through the instance table, repeating events are
expanded by the platform, including their exceptions.

The description, attendees, organizer address, reminders, and every
other provider column are never read. Attendee addresses are other
people's data and never cross the bridge.

## Writing one event

Writes target the user's own calendars and are validated before any
provider call:

| rule | bound |
| --- | --- |
| title / location | at most 200 characters, no control characters |
| range | `begin` before `end`, at most 24 hours long |
| start time | at most 24 hours in the past, at most 366 days ahead |
| all-day | range must be whole UTC days, at least one day long |
| target calendar | access level contributor or better |

An insert without `calendar_id` goes to the primary writable calendar,
or to the first writable one when no calendar is marked primary. A
calendar the user only reads answers `calendar-read-only`; an event
that no longer exists answers `calendar-not-found`.

Setting `all_day` to `true` requires the range in the same call, because
the whole-day rule is checked against it. Pass `all_day` = `false`
(`--timed`) to turn an all-day event back into a timed one.

## Commands

```sh
# the next seven days
nusadesk-android calendar list

# create an event from epoch milliseconds
nusadesk-android calendar add --title 'Rapat' \
  --begin-ms 1760003600000 --end-ms 1760007200000

# move or rename it later
nusadesk-android calendar update 500 --title 'Rapat baru'

# remove it
nusadesk-android calendar delete 500
```

A write reports `written` = `true` and the affected `event_id`.
`calendar add` requires `--title`, `--begin-ms`, and `--end-ms`;
`calendar update` requires the event id and at least one change;
`calendar delete` requires only the event id. The CLI builds the
bounded parameters from these typed flags, so an unknown parameter
cannot be expressed and never reaches the app.

## Errors

| error | meaning |
| --- | --- |
| `calendar-permission-required` | no calendar grant yet |
| `calendar-permission-denied` | the user refused or revoked it |
| `calendar-unavailable` | no provider or no writable calendar |
| `calendar-invalid-argument` | a parameter failed a bound above |
| `calendar-read-only` | the target calendar is not writable |
| `calendar-not-found` | the event id does not exist |
| `calendar-failed` | the provider refused the write |

## Notes

- All-day events are stored on UTC day boundaries; treat `begin_utc_ms`
  and `end_utc_ms` as dates for them, not as local wall-clock times.
- Rows come from whichever calendars the Android Calendar app shows,
  including read-only ones the user subscribed to; only writable ones
  accept a write.
- The bridge keeps no calendar state: every read and write goes to the
  provider, and the audit line records only the operation and ids,
  never the title or location.
