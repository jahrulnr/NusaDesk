# The guest environment

Read this before assuming stock PRoot behaviour. The NusaDesk
app owns the session; everything below is a deliberate product
contract, not a PRoot default.

## PRoot, not a VM

- An Ubuntu Base ARM64 userland translated by PRoot - no
  kernel, no VM, no container daemon.
- Guest root is still the Android app's uid: no mount(2), no
  raw hardware beyond the fixed `/dev` bind, no kernel changes.
  Platform denials are real - an
  app uid cannot run `pm`, `am`, `dumpsys`, or `screencap`.
- The device's `/system/bin` and `/system/lib64` trees are
  bound at identical paths but never on `PATH`; reach them
  through `android-cli` so the Ubuntu userland is not
  shadowed.

## Session lifecycle

- The guest SSH endpoint is fixed at `127.0.0.1:22022`; a bind
  conflict is a typed failure, never a move to another port.
- The app owns lifecycle under a user-visible foreground
  service. Do not kill `sshd`, `lw-session-supervisor`, or
  `systemctl init` - they are the session you are inside.
- `/tmp` and `/dev/shm` are wiped at every session start, and
  `/run` holds per-session state (the bridge env, service
  markers, pid files). Nothing durable belongs in either.
- `/root`, `/home`, `/opt`, `/usr/local`, `/etc`, `/var/lib`
  persist across sessions and sit inside the guest backup
  scope.

## Workspace and Android files

- `/root/nusadesk` (`~/nusadesk`) is the workspace bind - the
  folder the user picked in the Android picker, real host
  storage other Android apps can see. On Android 10 it is the
  app's own external folder instead. It is absent when no
  usable folder exists - check before relying on it. Being a
  bind to shared storage it is not part of the guest backup.
- `saf.*`, `storage.get`, `share.send`, and `download.request`
  reach Android's own storage providers; their `termux-*`
  clients are optional.
- `nusadesk-serve` exposes a directory over plain HTTP on the
  LAN - reads and unauthenticated PUT/POST uploads under the
  served root; it prints a loud warning - and
  `nusadesk-net lan-ip` prints the address to hand out.

## Services (systemctl3, not systemd)

- `systemctl` and `service` are the vendored systemctl3
  bridge, not systemd - no journald and no real boot.
- `systemctl init` ran when the session started. Only units
  enabled before that init are restart-supervised this
  session; enabling mid-session does not supervise the unit
  until the next init.
- `systemctl stop` on an enabled unit does not survive a
  session restart - `disable` the unit when the stopped
  state must persist.
- `systemctl --user` has its own manager (`default.target`)
  under the same enabled-at-init rule.

## Containers (`udocker compose`)

- `udocker` is a product-owned wrapper over digest-pinned
  sources; `udocker install` is rejected because NusaDesk
  supplies the inner PRoot.
- `udocker compose -f FILE up -d | down | stop | start | ps |
  logs [SERVICE]` is the supported flow. `up -d` persists a
  plan; the product `lw-compose-supervisor` (or `udocker
  compose-supervise --all`) is the only restart authority -
  the CLI never starts containers itself.
- `ports:` is rejected outright: udocker on PRoot strips the
  bind address, so a '127.0.0.1' publish could still land on
  the LAN. Keep services guest-internal.

## Optional toolkits

Installed only by user choice (at setup, or later from
System) - check `command -v` before relying on either:

- `termux-*` commands + `docs/termux-compat.md` - Termux:API
  clients over the bridge (capture, SAF, dialogs, TTS, NFC,
  fingerprint, keystore, job scheduler, and more).
- `nusadesk-usb`, `nusadesk-usbd`, and the wrapped `adb` - USB
  pass-through; the stock guest `adb` sees devices attached
  to the phone's USB port.

## Reaching Android

- `nusadesk-*` and `termux-*` clients talk to the capability
  bridge - see [bridge.md](bridge.md) for the transport and
  methods.
- `android-cli` runs the device's own binaries as the app uid
  (`status`, `doctor`, `permissions`, `getprop`, `toybox`,
  `toolbox`, `sh`, `exec`); `su` is the root tier on rooted
  devices (one Magisk prompt per grant).
- A denied grant is an honest boundary, not a bug:
  `android-cli permissions` lists grant states and
  `permission.request` opens the user-visible consent or
  Settings flow.
